# 5. 記録とメタデータ — `csikit record`・記録のファイルの中身・条件の書き方

[目次](README.md) ・ 前: [4. モニタの読み方](04_monitor.md) ・ 次: [6. 解析の入口](06_analysis_intro.md)

この章のゴール: **`uv run csikit record` で CSI を記録し、記録の条件（メタデータ）を書いて、後から誰が見ても「いつ・どこで・何をした記録か」が分かる状態にする**こと。
そして、記録のファイルの 1 行が何でできているか、壊れた行をどうやって見つけているかが分かること。

用意するもの: 4 章でモニタが約 100 Hz を示した状態。モニタは閉じておきます（1 つのポートは同時に 1 つのアプリしか使えません）。

---

## 5-1. 記録する — 「動画の録画ボタン」

🌱 **ファーストタッチ**

スマホのカメラでは、プレビュー（4 章のモニタ）を見ながら構図を決めて、録画ボタンを押します。
`csikit record` は、その録画ボタンです。決めた秒数だけ、受信機が送ってくる CSI をそのままファイルに残します。

```sh
uv run csikit record --duration 30 --label empty
```

- `--duration`: 記録する時間 [秒]
- `--label`: 何の記録かを表す短い名前（英数字・`_`・`-`）。例: 誰もいない部屋なら `empty`、手を振るなら `wave`

終わると、次のように出ます（2026-10-28 に 20 秒記録したときの例）。

```
受信機（R1）: /dev/ttyACM1
記録中 20 秒 → …/m5stack-csi-kit/data/raw/20261028-093000-kitfw-test.csv
メタデータの下書き: …/m5stack-csi-kit/data/meta/20261028-093000-kitfw-test.toml（TODO 17 件を埋めてください）
ok=2008 bad_crc=0 bad_ratio=0.0000 bad_format=0 other=2 span_sec=20.10 rate_hz=99.9 est_missing=6 seq_unknown=0 missing_seq=3
```

🌿 **しくみ** — 最後の 1 行（記録の成績表）の読み方

| 項目 | 意味 | この例 |
|---|---|---|
| `ok` | 記録した CSI の行の数 | 2008 行（20 秒 × 約 100） |
| `bad_crc` | 壊れていたので捨てた行（5-3） | 0 |
| `bad_format` | 形が違って読めなかった行（受信機と PC の版が違うときなど） | 0 |
| `rate_hz` | 1 秒あたりの行の数 | 99.9 |
| `missing_seq` | 連番の飛びから数えた欠け（4 章の `loss` と同じ考え方） | 3（0.15 %） |
| `est_missing` | 受信の時刻の間隔から見積もった欠け（連番が使えないときの目安） | 6 |

- 記録は `data/raw/<日時>-<label>.csv`、条件の下書きは `data/meta/<同じ名前>.toml` にできます。名前に日時が入るので、同じ label で何回取っても上書きされません
- 記録中は**受信機をリセットしません**。記録の始めに `WHO` を送り、その返事（受信機・送信機の MAC、チャンネル）も記録に残します
- `data/` は **git に入りません**（`.gitignore`）。記録には部屋の様子が映りうるので、人に渡すときは 1 章 1-6 と 8 章を読み返します
- 記録とメタデータには、M5Stack Basic の MAC が入っています。人に渡す・公開するときは、ダミーに置き換えた写しを作って渡します:
  `uv run python scripts/mask_macs.py data/raw/<名前>.csv --out-dir <写しの置き場>`（元のファイルは書き換えません）

🌳 **もう一段** — 記録の名前は、なぜ日時から始まるの？

> この節は、**今は分からなくても先へ進んでかまいません**。

**まず、たとえで全体を見ます。** スマホの写真の名前は `IMG_20261028_093000.jpg` のように日時から始まることが多く、名前の順に並べれば撮った順になります。
記録の名前も同じで、`20261028-093000-…` は「2026 年 10 月 28 日 9 時 30 分 00 秒に始めた記録」です。

**次に、自分の目で確かめます。** 記録の名前から、日時とラベルを取り出します（実機は要りません）。

```sh
uv run python -c "from csikit import io; print(io.recording_name('data/raw/20261028-093000-empty.csv'))"
```

`20261028-093000-empty` と出れば正解です。この名前が、記録とメタデータを結ぶ鍵になります。

**分かったこと**

- 記録（`.csv`）とメタデータ（`.toml`）は、同じ名前でひと組。名前を変えると組が分からなくなるので、変えない

**今は分からなくてよい所:** 記録の中の `#` で始まる行（受信機の 1 秒ごとの報告 `# stats` など）の全部の項目。

## 5-2. メタデータ — 「写真のアルバムのメモ」

🌱 **ファーストタッチ**

旅行の写真も、1 年たつと「これはどこで撮ったんだっけ」となります。アルバムに「どこで・誰と・何をしていたか」をメモしておけば、後で迷いません。
記録も同じで、数字だけ残しても、**後から「何をした記録か」が分からなければ使えません**。そのメモを**メタデータ**と呼びます。

🌿 **しくみ**

`record` は、分かることを自動で書いた下書き（`.toml`）を作ります。自動で書けない項目は `TODO` になっています。
テキストエディタで開き、`TODO` を埋めます。分からない値は `"unknown"` と書きます（省かない）。

| 区切り | 書くこと（例） | 自動で入るもの |
|---|---|---|
| 先頭 | `purpose`（何を確かめる記録か）・`experiment`（実験の呼び名） | `recording`・`label` |
| `[time]` | — | 始めた時刻・長さ |
| `[[devices]]` | `name`（`T1`・`R1`）・`board`（`M5Stack Basic`） | 役割・MAC |
| `[radio]` | `tx_rate_hz`（`100`） | チャンネル・帯域 |
| `[placement]` | 部屋の呼び名（`room-A` など）・2 台の距離 [m]・間をさえぎる物があるか | — |
| `[environment]` | 部屋にいた人数・ほかに起きていたこと | — |
| `[[subjects]]` | 人の呼び名（`P1` など）と役割 | — |
| `[[segments]]` | 何秒から何秒に何をしていたか（`static`・`wave` など）と、どこで | — |
| `[quality]` | — | 受信レート・欠け・壊れた行・RSSI の平均 |
| `[status]` | `usable`（解析に使える記録か: `true`・`false`）・`issues`（気になったこと） | — |

**実名・住所は書きません。** 人は `P1`、部屋は `room-A` のような呼び名にします。書き方の見本は `examples/meta/` にあります。

埋め終わったら、点検します。

```sh
uv run python scripts/check_meta.py
```

`TODO` が残っていると「未記入」と出ます。全部埋まれば「問題なし」になります。

🌳 **もう一段** — `TODO` を残すと、どうなる？

> この節は、**今は分からなくても先へ進んでかまいません**。

**まず、たとえで全体を見ます。** 申込書の空欄に「未記入」の印を付けておけば、窓口で「ここが空いています」と教えてもらえます。
`TODO` はその印です。空欄のままにせず、わざと目立つ文字を入れておくことで、**埋め忘れを道具で見つけられる**ようにしています。

**次に、自分の目で確かめます。** キットの見本（埋めてある）と雛形（`TODO` を含む）で、未記入の項目を数えます（実機は要りません）。

```sh
uv run python -c "from csikit import meta; print(len(meta.find_todos(meta.load_meta('examples/meta/20260101-120000-static.toml'))))"
```

`0` と出れば正解です（見本は全部埋まっている）。自分の記録の下書きでは、同じ命令が `TODO` の数を返します。

**分かったこと**

- メタデータの形は決めてあり（[ADR 0003](../decisions/0003-recording-metadata-format.md)）、`check_meta.py` が形と埋め忘れを見る

**今は分からなくてよい所:** TOML の書き方の細かい決まり。同じ値をまとめて書く道具（`scripts/fill_meta.py`）。

## 5-3. 記録のファイルの 1 行 — 「宅配便の伝票」

🌱 **ファーストタッチ**

宅配便の伝票には、送り主・受け取り日時・荷物の中身・重さが決まった欄に書いてあります。
記録の CSI の 1 行も、**決まった順番の欄**でできています。最初が見出し（いつ・誰から・何番目・強さ）、最後が中身（56 本の CSI）です。

🌿 **しくみ**

```
CSI,<受信時刻 µs>,<送信元の MAC>,<連番>,<RSSI>,<雑音>,<チャンネル>,…,<区間>,<長さ>,<CSI の 16 進>*<CRC>
```

- `CSI,` で始まる行が 1 パケット（0.01 秒ごとに 1 行）。`#` で始まる行は受信機からのお知らせ（1 秒ごとの報告など）
- 欄の全部の意味は [受信機の README の「出力」](../../firmware/csi-rx/README.md) にあります
- 記録を Python で読むときは、キットの `csikit.io.load_rx_csv` を使います（6 章）。自分で欄を数えて読む必要はありません
- 記録は大きくなります（1 時間で約 120 MB）。しまうときは圧縮します: `uv run python scripts/raw_store.py compress <記録.csv>`（元と同じに戻せることを確かめてから `.csv.zst` を作る）

🌳 **もう一段** — 壊れた行に、どうやって気づくの？

> この節は、**今は分からなくても先へ進んでかまいません**。

**まず、たとえで全体を見ます。** 銀行の口座番号やバーコードには、最後に「チェック用の数字」が付いていて、1 桁でも打ち間違えると計算が合わなくなります。
CSI の 1 行の最後の `*` の後ろの 8 文字（**CRC**）も、同じ役目です。受信機が行の中身から計算して付け、PC が同じ計算をして比べます。
USB の途中で 1 文字でも化ければ、計算が合わないので、その行は捨てて `bad_crc` に数えます。

**次に、自分の目で確かめます。** 練習用の行を作って、正しく読めることと、1 文字変えると読めなくなることを見ます（実機は要りません）。

```sh
uv run python examples/tutorial/csi_line_demo.py
uv run python examples/tutorial/csi_line_demo.py --break
```

2 つ目は、連番の数字を 1 文字だけ変えています。次のように出れば正解です。

```
連番の 1 文字を変えました
読めません: CRC が一致しません（転送中に壊れた行） → この行は捨てて、bad_crc に数えます
```

**式で書くと:**

- CRC = CRC-32（行の `*` より前の文字列）。8 桁の 16 進で書く
- たまたま化けた行の CRC が合ってしまう確率は、およそ 2⁻³² ≈ 2.3 × 10⁻¹⁰（約 43 億行に 1 行）

**分かったこと**

- 壊れた行は記録に入れず、数だけ残す。だから `bad_crc` が増えたら、ケーブルや USB を疑う

**今は分からなくてよい所:** CRC-32 の計算の中身。8 章の署名（HMAC）との違い（CRC は「偶然の化け」を見つける道具で、わざと書き換える相手には効かない。署名は鍵が無いと作れない）。

## 確かめよう

1. `csikit record --duration 60 --label wave` で記録すると、ファイルはどこに、どんな名前でできる？
2. 成績表の `missing_seq=3` と `bad_crc=0` は、それぞれ何が起きたことを表している？
3. メタデータの `TODO` を、分からないからといって消してしまうのは良い？
4. CRC と 8 章の署名は、どちらも「最後に付く数字」。何が違う？

<details>
<summary>答え</summary>

1. `data/raw/<日時>-wave.csv`（例: `20261028-093000-wave.csv`）。条件の下書きは `data/meta/<同じ名前>.toml`
2. `missing_seq=3`: 送信機が送ったうち 3 個を受信機が受けられなかった（無線の区間の欠け）。`bad_crc=0`: USB の途中で壊れた行は無かった
3. 良くない。分からなければ `"unknown"` と書く。消すと、点検で「必須項目がない」になり、後から何が分からなかったのかも分からなくなる
4. CRC は偶然の化けを見つける（誰でも計算できる）。署名は鍵を持つ相手しか作れず、わざと書き換えた命令を見つける

</details>
