## 条件

- 機材: M5Stack Basic 2 台（USB 変換チップ CH9102。元の研究で使ってきた T1（送信機）・R1（受信機））
- ファーム: 元の研究のまま。送信機 `fw=1010-870873a`（v4）、受信機 `fw=1014-ba5e05b`。このキットのファームは**書き込んでいない**
- PC: ChromeOS の Linux（Crostini）、Python 3.14、pyserial 3.5。ポートは `/dev/ttyACM0`（送信機）・`/dev/ttyACM1`（受信機）
- 2 台は机の上。距離・置き方は記録していない
- MAC はここに書かない（公開するリポのため）

## 1. 最初の doctor が NG（ポートを開くと再起動する）

`csikit doctor` が 2 台とも「WHO に答えない」。何も送らずに読むと、開くたびに `rst:0x1 (POWERON_RESET)` から起動していた。
起動の途中で WHO の待ちが切れていた。

## 2. 開き方の比較（送信機・各 3 回）

開いてから 2.5 秒の間に起動の表示（`rst:`）が出たかで見た。

| 開き方 | 再起動 |
|---|---|
| A 開く前に `dtr = False`・`rts = False`（それまでの `open_no_reset`） | 3 回中 3 回 |
| B 普通に開く | 3 回中 0 回 |
| C 普通に開いてから `rts = False` → `dtr = False` | 3 回中 0 回 |
| D 普通に開いてから ioctl で 2 本同時に下げる | 3 回中 0 回 |

- 推定の理由: Linux では開いた瞬間にカーネルが DTR/RTS を両方上げ、pyserial が DTR → RTS の順に 1 本ずつ下げる。
  その間の「DTR だけ下がり RTS は上がっている」瞬間が、ESP32 の自動リセット回路では EN を下げる組み合わせになる
  （回路は一般的な ESP32 の自動リセット回路の記憶。M5Stack Basic の回路図では確かめていない）
- C で開き直しを 4 回: 送信機の連番 `seq=` は 7100 → 7600 → 8000 → 8500 と続いた（**閉じても再起動しない**）
- C で受信機を 3 回開いて WHO: 3 回とも再起動せず応答。受信数 `matched` も増え続けた
- 元の研究の未解決「ポートを開くと受信機がリセットされることがある（毎回ではない）」は、B に近い開き方ではまれにしか起きない、
  という話と矛盾しない（B は 3 回だけなので、まれに起きるかは分からない）

→ `ports.open_no_reset` を C に直した。順番はテスト（`tests/test_ports.py`）で固定。
